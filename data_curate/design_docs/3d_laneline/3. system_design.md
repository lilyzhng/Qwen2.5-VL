# 3. System Design

## 3.1 Front-End Detector Selection

| Criterion | Option 1: Add lane-line head to HulkUM v2 | Option 2: SAM3 + LiDAR lifting |
| :---- | ----- | ----- |
| Delta | Detection module is trained in-house (3D/BEV output) | Detection module is off-the-shelf (2D masks + tracking) |
| Time | Medium (needs training integration + iterations) | Fast (mostly inference + projection + fitting) |
| Shared required work | Same for both: pose alignment → aggregation/denoise → association/re-ID → polyline/spline fitting | Same for both: pose alignment → aggregation/denoise → association/re-ID → polyline/spline fitting |
| Engineering + compute cost | High (training infra + GPU cycles) | Low (inference only) |
| Impact to existing 3DOD | High (observed negative transfer/regression in the past) | Low (decoupled from 3DOD training) |
| Performance | Higher if we have good quality labels and can iterate safely | Good for MVP; may need finetune/training to match best-in-class |

**Trade-off:** Option 1 vs 2 is mainly a choice of the front-end detector + impact on 3DOD + infra cost. The post-detection refinement pipeline (aggregation, association, polyline fitting) is required either way.

**Historical Context:** In HulkUMv1, adding a lane-line-specific head ([BEV-laneDet](https://github.com/latai-pd/av/blob/main/kits/ml/pytorch/heads/lanes/bev_lane_head.py)) impacted object detection performance. Even with detached gradients, regression was observed. Alternating training regimes (training 3DOD head for N iterations with lane head fixed, then vice versa) could mitigate this.

**Recommendation:** Start with Option 2 (SAM3 + LiDAR) for MVP to avoid 3DOD regression risk. Evaluate Option 1 for future iterations if higher accuracy is needed.

## 3.2 Why a Refinement Pipeline Is Required

Regardless of which front-end detector is used, raw per-frame outputs are **insufficient for auto-labeling** and require a downstream refinement stage. This section explains why.

### 3.2.1 Limitations of Raw Detector Outputs

**Problem 1: Sparse and Incomplete Coverage**

A single LiDAR sweep or camera frame provides only a partial view of each lane line. The vehicle sees different portions of the lane as it moves, but any individual frame captures only a narrow spatial window.

| Source | Limitation |
| :---- | :---- |
| LiDAR points hitting lane markings | Sparse at long range; paint reflectivity varies; occlusion from other vehicles |
| 2D lane masks | Dense in image space, but depth must be inferred from LiDAR—many pixels have no corresponding LiDAR return |
| BEV lane detections | Fixed perception range (typically 50–80 m ahead); no backward coverage |

**Problem 2: Per-Frame Noise and Jitter**

Individual detections exhibit frame-to-frame noise due to:
- Sensor noise (camera exposure, LiDAR return intensity)
- Network inference variance
- Slight calibration/timing errors between camera and LiDAR

Directly concatenating per-frame outputs produces a "spaghetti" of overlapping, inconsistent polylines rather than clean lane annotations.

**Problem 3: Tracking Fragmentation**

Front-end trackers (e.g., SAM3's video tracker, or per-frame Hungarian matching) assign instance IDs that may:
- Reset at scene cuts or occlusions
- Fragment a single physical lane into multiple track IDs
- Merge distinct lanes under one ID during lane changes or merges

These track IDs are **locally consistent within a tracking window** but are not globally consistent across the full slice.

**Problem 4: Downstream Consumer Requirements**

The downstream consumers of auto-labels require:
- **Smooth, editable polylines:** Labelers review and correct annotations; jagged or duplicated curves slow QA
- **Global instance IDs:** Each physical lane line needs a single ID across the slice for downstream map generation and UM training
- **World-frame coordinates:** Labels must be in a shared coordinate frame, not per-frame ego coordinates
- **Consistent attributes:** Lane type, color, and pattern must be resolved per instance, not per detection

### 3.2.2 Role of the Refinement Pipeline

The refinement pipeline addresses these gaps by:

1. **Accumulating observations along the trajectory:** Multiple frames viewing the same lane are fused in world coordinates, filling spatial gaps and increasing point density.

2. **Denoising via redundancy:** Outliers (false positives, misaligned points) are suppressed when they don't recur across frames; consensus geometry emerges from repeated observations.

3. **Re-associating across tracking resets:** Geometry-based association (3D proximity, tangent consistency) links fragments that the front-end tracker separated, producing stable global IDs.

4. **Fitting smooth curves:** Raw point clouds are converted into parametric curves (splines or polylines) that are smooth, continuous, and easy to edit.

This is analogous to how lane mapping systems accumulate lane observations over a trajectory and fit smooth curves to the aggregated data—but scoped to a **single slice** without global map association or loop closure.

## 3.3 System Architecture

### 3.3.1 Scope and Assumptions

**Scope:** Offboard auto-labeling pipeline for 3D lane lines. Produces per-slice annotations for human review and downstream training.

**Assumptions:**
- Reliable LiDAR SLAM / odometry provides ego pose for each frame (we assume SLA or equivalent is available and accurate).
- Camera-LiDAR calibration and time synchronization are correct.
- Processing is offline/batch; we can use bidirectional (forward + backward) information.

**Out of Scope:**
- Global HD map building (no loop closure, no multi-trip aggregation)
- Online/real-time perception (no latency constraints)

### 3.3.2 Pipeline Overview

```
┌────────────────────────────────────────────────────────────────────────────┐
│                           FRONT-END DETECTOR                               │
│  (HulkUM v2 lane head OR SAM3 + LiDAR lifting)                             │
│  Output: Per-frame 3D lane points + per-frame track IDs                    │
└────────────────────────────────────────────────────────────────────────────┘
                                      │
                                      ▼
┌────────────────────────────────────────────────────────────────────────────┐
│                         REFINEMENT PIPELINE                                │
│                                                                            │
│  ┌──────────────┐   ┌──────────────┐   ┌──────────────┐   ┌─────────────┐  │
│  │ Pose-Aligned │──▶│  Multi-Frame │──▶│  Geometry-   │──▶│   Curve     │  │
│  │ Accumulation │   │  Denoising   │   │  Based Assoc │   │   Fitting   │  │
│  └──────────────┘   └──────────────┘   └──────────────┘   └─────────────┘  │

```

### 3.3.3 I/O Specification

**Inputs:**
- Camera frames (all cameras)
- LiDAR scans
- Camera-LiDAR calibration (extrinsics, intrinsics)
- Ego pose per frame (from SLA / LiDAR SLAM)

**Outputs:**
- 3D lane polylines in world coordinates
- Global lane instance ID per polyline (unique within slice)
- Per-polyline attributes: lane type (center/lane/edge), color, pattern (solid/dashed)
- Timestamps for each polyline (frame range)

## 3.4 Refinement Pipeline: Detailed Design

### 3.4.1 Stage 1: Pose-Aligned Accumulation

**Purpose:** Transform per-frame lane points from ego/LiDAR frame to a shared world frame, enabling multi-frame fusion.

**Process:**
1. For each frame `t`, receive 3D lane points `P_t` in ego frame and ego pose `T_world_ego(t)`.
2. Transform: `P_world = T_world_ego(t) · P_t`
3. Associate points by front-end `track_id` (within tracking window).
4. Accumulate points across frames, grouped by `track_id`.

**Output:** Per-track point clouds in world coordinates.

**Key Consideration:** Accumulation quality depends on pose accuracy. With reliable LiDAR SLAM, pose errors are typically < 10 cm over a slice, which is acceptable for lane-level precision.

### 3.4.2 Stage 2: Multi-Frame Denoising

**Purpose:** Remove outliers and reduce noise in the accumulated point clouds.

**Techniques:**

| Technique | Description | When to Use |
| :---- | :---- | :---- |
| Statistical outlier removal | Remove points with mean neighbor distance > k·σ | Always; removes isolated noise |
| Voxel downsampling | Grid-based averaging to uniform density | Always; reduces redundant points |
| RANSAC line/curve fitting | Fit model, reject inliers outside threshold | If significant outliers remain |
| Observation count filtering | Remove lanes with < N observations | Always; suppresses false positives |

**Parameters (initial values):**
- Voxel size: 0.2 m (lateral) × 0.5 m (longitudinal)
- Min observations per lane: 4 frames
- Outlier threshold: 2σ from local mean

**Output:** Cleaned, downsampled point clouds per track.

### 3.4.3 Stage 3: Geometry-Based Association

**Purpose:** Link track fragments into globally consistent lane instances. The front-end tracker provides locally consistent IDs, but tracking resets (occlusions, scene cuts) fragment physical lanes into multiple tracks. This stage re-associates fragments using geometric cues.

**Association Criteria:**

| Criterion | Implementation |
| :---- | :---- |
| 3D proximity | Endpoint distance < threshold (e.g., 2 m) |
| Tangent consistency | Direction at endpoints aligns within ±15° |
| Overlap ratio | If tracks overlap spatially, require > 70% point overlap to merge |
| Lateral sequence consistency | If lane A is left of lane B in one segment, it should remain left of B in the associated segment |

**Association Algorithm:**
1. Build candidate pairs: (track_i, track_j) where endpoints are within proximity threshold.
2. Score each pair by tangent alignment + overlap.
3. Greedy or Hungarian matching to assign global lane IDs.
4. Handle merges/splits: If a track's points diverge (e.g., at a lane split), create new global IDs for the branches.

**Output:** Global lane ID assigned to each point cloud.

### 3.4.4 Stage 4: Curve Fitting

**Purpose:** Convert the fused, denoised point cloud into a smooth, parametric curve suitable for labeling output.

**Fitting Method:** Control-point-based spline (B-spline or Catmull-Rom).

**Why Splines?**
- Smooth and continuous (C1 or C2)
- Editable: labelers can adjust control points
- Compact: fewer parameters than dense polyline
- Well-suited for curve optimization (can add smoothness priors)

**Process:**
1. **Control point initialization:** Place control points at regular intervals (e.g., 3 m chord length) along the point cloud skeleton.
2. **Spline fitting:** Optimize control point positions to minimize distance to data points + smoothness regularization.
3. **Resampling:** Evaluate spline at fixed intervals (e.g., 0.5 m) to produce final polyline output.

**Smoothness Regularization:**
- Penalize second derivative (curvature) to avoid zigzag
- Optionally use Huber loss for robustness to remaining outliers

**Output Format:**
- `poly3d` label type, layer `lane_line3d_bev_user`
- List of (x, y, z) coordinates, ordered in direction of travel
- Attributes: type, color, pattern

## 3.5 Design Decisions

### 3.5.1 2D-to-3D Lifting Method (SAM3 + LiDAR Option)

When using SAM3 for 2D lane segmentation, 3D points are obtained by LiDAR projection:

**A. Forward Projection (Recommended):** Project LiDAR points into the image; keep points inside the 2D lane mask.
- Pros: Physically grounded; only uses actual LiDAR returns; robust to thin lanes (can dilate mask).
- Cons: Sparse at long range; coverage depends on LiDAR pattern.

**B. Inverse Projection:** For each lane pixel, find nearest LiDAR point and assign its depth.
- Pros: Can sample densely along lane skeleton.
- Cons: Many pixels have no nearby LiDAR return; interpolation can "snap" to wrong surfaces (curb, vehicle).

**Decision:** Use Forward Projection as the primary method. Use Inverse Projection only for densification after initial curve fitting (resample the fitted curve, not raw LiDAR).

### 3.5.2 Spline Parameterization

| Option | Pros | Cons |
| :---- | :---- | :---- |
| Cubic B-spline | C2 continuous; well-supported in optimization libraries | Control points do not lie on curve |
| Catmull-Rom spline | Control points lie on curve (intuitive for editing); C1 continuous | Slightly less smooth than B-spline |
| Polyline (piecewise linear) | Simple; no optimization needed | Not smooth; many points needed |

**Recommendation:** Catmull-Rom spline for initial implementation due to intuitive control point placement. Evaluate B-spline if higher smoothness is required.

**Control Point Spacing:** 3 m chord length (adjustable based on road curvature).

### 3.5.3 Bidirectional Processing

Since this is an offboard pipeline, we can process the slice in both directions:
- **Forward pass:** Accumulate and associate from start to end.
- **Backward pass:** Re-associate using future context to fix early tracking errors.
- **Merge:** Combine forward and backward results, preferring higher-confidence associations.

This leverages the full slice context, unlike online systems that are causal.

## 3.6 Handling Edge Cases

### Lane Merges and Splits

At merge/split points, a single lane may become two (or vice versa). Handle by:
1. Detecting divergence in the aggregated point cloud (e.g., points spread into two clusters).
2. Fitting separate curves to each branch after the split point.
3. Assigning new global IDs to the branches while recording the merge/split relationship in metadata.

### Occlusions and Gaps

If a lane is occluded (by a truck, construction barrier):
1. The front-end will produce a gap in detections.
2. During association, connect fragments on either side of the gap if tangent and lateral position are consistent.
3. During curve fitting, interpolate smoothly across the gap (spline naturally interpolates).

### Construction Zones

Temporary lane markings (cones, temporary paint) may override permanent markings:
1. Rely on the front-end detector to segment the visible markings.
2. The refinement pipeline does not distinguish temporary vs. permanent—it produces labels for what is visible.
3. Downstream consumers (or human labelers) can flag temporary markings.

## 3.8 Dependencies and Assumptions

### Pose / Trajectory

We assume reliable LiDAR SLAM or SLA provides ego pose per frame. Pose errors < 10 cm (translational) and < 0.5° (rotational) are acceptable for lane-level precision. If pose quality is poor, aggregation will produce "ghosting" or smeared lanes—this is a failure mode that must be addressed at the pose estimation stage, not in this pipeline.

### Calibration

Camera-LiDAR extrinsics must be accurate to project LiDAR points into image masks. Calibration errors manifest as systematic offsets in the 3D lane positions. Time synchronization errors cause similar artifacts.

### Front-End Detector Quality

The refinement pipeline can suppress noise and fill gaps, but cannot recover lanes that the front-end completely fails to detect. Detector recall is a prerequisite for auto-labeling coverage.

## 3.9 SAM3 Fine-Tuning (If Using Option 2)

If using SAM3 + LiDAR lifting:

**Model Architecture:**
- SAM3: detector + tracker sharing a vision encoder (848M parameters)
- Detector: DETR-based, conditioned on text/geometry prompts
- Tracker: SAM2-based transformer for video segmentation

**Fine-Tuning Approach:**
- Fine-tune detector components only (image model) using differential learning rates
- Use `build_sam3_image_model` for detector-only fine-tuning
- Video fine-tuning is less documented; evaluate third-party approaches if needed

**Data Requirements:**
- Format: Video instance segmentation with consistent instance IDs
- Volume: ~1k diverse samples, ~500 video sequences

**Prompt & Ontology:**
- Map text prompts to lane ontology via versioned configuration
- Reference: `autonomy/maps/pom/tools/labels_to_um.py`

## 3.10 Summary

| Stage | Input | Output | Purpose |
| :---- | :---- | :---- | :---- |
| Front-End Detector | Camera + LiDAR | Per-frame 3D points + track IDs | Raw lane detection |
| Pose-Aligned Accumulation | Per-frame points + ego pose | World-frame point clouds per track | Multi-frame fusion |
| Multi-Frame Denoising | Accumulated point clouds | Cleaned point clouds | Remove noise/outliers |
| Geometry-Based Association | Cleaned point clouds + track history | Global lane IDs | Link fragments |
| Curve Fitting | Point clouds with global IDs | Smooth 3D polylines | Produce final output |

The refinement pipeline is essential for producing auto-labels that meet downstream requirements: smooth, globally-consistent, world-frame polylines suitable for human review and model training.
