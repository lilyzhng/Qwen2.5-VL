### 3.1 Add Laneline Head vs Off-the-shelf Model

| Criterion | Option 1: Add lane-line head to HulkUM v2 | Option 2: SAM3 \+ LiDAR lifting |
| :---- | ----- | ----- |
| Delta | Detection module is trained in-house (3D/BEV output) | Detection module is off-the-shelf (2D masks \+ tracking) |
| Time | Medium (needs training integration \+ iterations) | Fast (mostly inference \+ projection \+ fitting) |
| Shared required work | Same for both: pose alignment → aggregation/denoise → association/re-ID → polyline/spline fitting | Same for both: pose alignment → aggregation/denoise → association/re-ID → polyline/spline fitting |
| Engineering \+ compute cost | High (training infra \+ GPU cycles) | Low (inference only) |
| Impact to existing 3DOD | High (observed negative transfer/regression in the past) | Low (decoupled from 3DOD training) |
| Performance | Higher if we have good quality labels and can iterate safely | Good for MVP; may need finetune/training to match best-in-class |

Trade-off: Option 1 vs 2 is mainly a choice of the front-end detector \+ impact on 3dod \+ infra cost. The post detection flow (aggregation, association, polyline fitting) is required either way.

### 3.2 Workflow

#### I/O

* Inputs: Camera, LiDAR, camera LiDAR calibration, Pose
* Outputs: 3D lane graph/lane polylines with global IDs timestamps

#### Steps

1. **2D lane segmentation \+ tracking**
   1. Input: camera frames
   2. Output: per-frame lane masks, with a slice-level track\_id for each lane instance, with IDs consistent within the tracking window.

2. **2D→3D lifting via LiDAR projection \+ mask gating (frame-level)**
   1. Input: mask, track\_id at frame t \+ LiDAR scan at t \+ camera LiDAR calibration, time sync
   2. Flow: project LiDAR points into the image; for each track\_id, keep LiDAR points whose projections fall inside that instance's mask
   3. Output: per-frame 3D point sets keyed by track\_id (i.e., {track\_id → sparse 3D points} for that frame).

3. **Pose transform to a common frame (world coordinates)**
   1. Input: per-frame 3D point sets \+ ego pose at time t.
   2. Flow: transform each frame's lane points from LiDAR/ego(t) into a shared frame (world coordinate).
   3. Output: time-aligned 3D point sets in a common coordinate frame.

4. **3D aggregation \+ denoise \-\> stable points**
   1. Input: multi-frame 3D points in common frame, grouped by track\_id.
   2. Flow: accumulate points across time, remove outliers (RANSAC, density filters), downsample, fill small gaps.
   3. Output: fused 3D point clouds per candidate lane instance.

5. **3D association / re-ID \-\> lane instances across sequences**
   1. Input: fused candidate lane point clouds \+ track\_id history.
   2. Flow: associate lane candidates over time using 3D proximity \+ tangent/heading consistency \+ overlap; handle tracking resets; merge/split; assign stable global lane IDs (may use a filter-based tracker).
   3. Output: per-lane-instance fused 3D points with global IDs.

6. **Geometry fitting \+ attribute extraction**
   1. Input: per-lane-instance fused 3D points.
   2. Flow: fit a structured representation (3D polyline / spline), enforce smoothness/continuity, infer attributes (dashed/solid).
   3. Output: 3D lane polylines/splines.




### 3.3 Design Choices

**Lifting 2D Lanes to 3D with LiDAR**
A. Forward Projection: LiDAR → image projection \+ mask gating

* Mechanism: Project every LiDAR point into the camera; keep points that land inside the 2D lane mask.
* Output: a sparse but physically valid set of 3D points on the lane/road surface.

B. Inverse Projection: Image → 3D ray using lidar depth

* Mechanism: for each lane pixel, cast a ray and assign a depth by finding a LiDAR return along that ray / nearest in angle.
* Output: a 3D point per chosen pixel sample, but many pixels won't have a matching LiDAR return.

|  | Strengths | Weakness |
| :---- | :---- | :---- |
| **A. Forward Projection** | Robust to thin lanes: you can dilate the mask/region and still capture enough points. Naturally handles multiple returns and occlusions: you keep whatever LiDAR actually saw. Easy to debug: you can visualize projected points over the mask and see alignment issues. | Point density depends on LiDAR pattern; you may miss lanes at long range if LiDAR doesn't hit paint/ground often. |
| **B. Inverse Projection** | Lets you sample along the lane shape (e.g., along a skeleton) which is nice for building a polyline. | Most lane pixels have no exact LiDAR match → you end up doing nearest-neighbor / interpolation in angular space, which can "snap" to wrong surfaces (curb, vehicle, road edge). More sensitive to calibration/time sync jitter, because you're forcing a depth for a pixel. Harder to guarantee you're staying on the ground surface unless you explicitly intersect with a ground model. |

Trade-off. Default: (1) LiDAR→image \+ mask gating is usually better because it's more conservative and physically grounded. Use (2) only as a secondary step after (1), not instead of it:

* Do (1) to collect reliable 3D support points.
* Fit a spline/polyline in BEV.
* If you want denser points along the curve, resample the fitted spline (this gives you dense geometry without inventing depth from sparse LiDAR).

### 3.4 Multi-Frame Aggregation and Mapping

Because a single LiDAR sweep or image can be sparse or noisy, many auto-labeling methods aggregate data across multiple frames or trips to improve coverage. A moving vehicle will see different parts of a lane over time, so merging frames can produce a continuous lane line. Early work at Stanford (Kiske, 2015) built a dense map of highway lanes by accumulating 20 hours of driving data.

### 3.5 Geometric Refinement

After extracting 3D lane points (from one frame or many), the next step is to represent each lane line as a smooth curve or polyline. Raw points can be noisy or gappy, so pipelines apply fitting algorithms to produce a clean continuous lane annotation. A common choice is to fit a spline or low-order polynomial through the points. For instance, [Baidu's LiSV-3DLane](https://arxiv.org/abs/2309.13596) work samples a set of lane points and then performs cubic curve interpolation to create a smooth lane shape through them. The result is a densely-sampled 3D curve (essentially a polyline) that follows the lane marking with high fidelity

Finally, once a curve is fit, further smoothing can be applied if needed. Simple averaging or low-pass filtering across frames helps reduce jitter in video annotations. The aim is a natural-looking lane line that doesn't zigzag due to sensor noise. Some pipelines explicitly smooth trajectories over time or adjust control points of the spline to enforce curvature continuity. The outputs are typically stored as polylines (a series of 3D points at fixed intervals) or parametric curves.

# Temporal Association and Tracking

When labeling lane lines in video sequences (or across multiple sensor passes), maintaining **temporal consistency** is critical. Unlike static images, lanes in a sequence must be tracked with persistent identities and shapes over time. A common practice is to assign each physical lane an ID and propagate that ID frame-to-frame so that the same lane is consistently labeled.
Interpolation between keyframes is used to speed up annotation: annotators can label a lane on frame 0 and frame 10, and the software will interpolate the lane positions in the intermediate frames. This works if the vehicle motion is smooth, but it risks "lane jumps" if the interpolation isn't perfect
